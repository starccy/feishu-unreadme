# 发送动作触发已读上报(方案 A)

日期:2026-05-14

## 背景

当前 `main.py` 在飞书前端 `updateMessagesMeRead` 上报点之前插入 `t.messageIds=[]`,无条件清空已读消息 ID 列表,从而屏蔽全部已读回执。副作用:用户主动回复对方消息后,对方仍然看到该消息为"未读",体验割裂——对方明明收到我的回复,却以为我没看到他原本的消息。

## 目标

- 用户在某会话**主动发送一条消息**时,允许该会话此前未读消息被上报为"已读"。
- 不在意上报范围细分:由飞书内部决定该上报哪些 ID 即可,本设计不重写上报内容。

## 非目标

- 不主动处理 README 中"已知问题"列出的"贴表情、引用回复、接收文件"三类入口。如果发送 hook 恰好命中其中一处,视为意外加分,不视为回归。
- 不区分群聊 / 单聊行为。
- 不引入用户可控的开关 UI,默认行为即新行为。

## 总体方案

1. 在飞书 webpack 全局加一个一次性放行计数器 `window.__feishuAllowMeReadCount`(整数,默认 0)。
2. 改造现有 `updateMessagesMeRead` 锚点处的注入逻辑:
   - 计数器 > 0:不清空 `messageIds`,计数减一。
   - 计数器 == 0:照常 `t.messageIds=[]`(维持当前屏蔽语义)。
3. 新增第二处 hook:在飞书"用户主动发送消息"的入口函数处,把计数器置为一个小整数(初值 2,以容错短时间内多次回调),让紧接其后的 `updateMessagesMeRead` 调用得以通行。

放行采用"消费即减"语义,不依赖 `setTimeout` 清零,避免残留导致后续意外放行。

## main.py 实现修改点

- `CODE_PATTERN` / `PAYLOAD` 从"单点替换"扩展为多组 `(pattern, payload)`:
  - **锚点 1(已有)**:`\w+\.\w+\.info\("updateMessagesMeRead"`
    - 注入语句(插入在变量名起始位置之前):
      ```
      if(window.__feishuAllowMeReadCount>0){window.__feishuAllowMeReadCount--}else{t.messageIds=[]};
      ```
    - 替换掉原来的 `t.messageIds=[],` payload。
  - **锚点 2(新增)**:用户主动发送消息的入口函数。
    - 字面匹配字符串在实现期间通过 grep 解包后的 js 文件确定。候选关键词:`sendMessage`、`MessageSend`、`info("sendMessage`、`info("send_message`,以及类似 `updateMessagesMeRead` 的 `info(...)` 调用日志埋点。
    - 选离 native bridge 调用最近、且每次"用户敲回车发消息"都会触发的那一处作为锚点。
    - 注入语句:
      ```
      window.__feishuAllowMeReadCount=2;
      ```
- `find_file` 改为接收并返回多组锚点(每组对应一个 pattern + payload + 命中文件 + 命中位置)。
- `modify_file` 改为按"文件 -> 多个 (offset, payload)"分组应用,保持插入顺序稳定(从大 offset 到小 offset 倒序插入,避免位移错乱)。
- 任意一组锚点未命中,视为版本不兼容:清理 unpacked 目录、报错退出,不打 patch。和现有 `not js_files -> 退出` 的行为一致。

## 风险与回退

- **R1 — 飞书发送消息后不会自动触发 `updateMessagesMeRead`**:放行计数器空跑,对方仍显示未读。回退路径:升级到方案 B(在发送回调里通过额外 hook 直接调用上报函数),工作量上升,需要额外逆向 store 与上报函数签名。
- **R2 — 发送入口锚点不稳定,版本一更就失效**:与现有脚本面临的问题同类。继续依赖飞书更新后重新匹配字符串解决,不在本设计范围内做长期兼容方案。
- **R3 — 计数器残留导致后续意外放行**:用消费即减 + 一次性置位规避;无定时器清零依赖。

## 测试方案

用主账号 + 测试号双向手工验证,逐项执行:

1. **回归 / 屏蔽看消息**:测试号 → 我发消息;我打开会话不回复 → 测试号侧应**仍显示未读**。
2. **新功能 / 发消息触发已读**:测试号 → 我发消息;我打开会话并回复一条普通消息 → 测试号侧此前未读消息应**变为已读**。
3. **放行严格性**:我回复后,测试号再发一条;我**不打开会话也不回复** → 该新消息应**仍未读**。
4. **群聊场景**:在群聊里重复执行步骤 1–3。

任何一步与预期不符,则方案 A 不可行,转入方案 B。
